# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Chicago District Explorer: a single-file, dependency-light web app. Click a point in Chicago (or search an address) and it reports every civic district containing that point and who represents you there — wards, county/state/federal legislative districts, police districts/beats, school zones, and more. Layers are location-aware: city layers hide outside Chicago, county layers appear only in the counties that publish them, and the statewide layers (county, township, municipality, school district, ZIP) work anywhere in Illinois. Deployed as a static site to `chidistricts.com` (see `CNAME`).

**Coverage is no longer "the Chicago collar."** It began as the seven metro counties and grew one contiguous county at a time across central and northern Illinois — north to the Wisconsin line, west to the Mississippi, and south through the Metro East to the Missouri border (**91 counties served, and since 2026-09-06 ALL 91 ARE ON THE DISPATCH TIER — the judicial and card-only tiers are empty for the first time, because the statewide library layer reached the last twelve counties that had no county-dispatched layer of their own (it was 79 dispatch / 2 judicial / 10 card as recently as 2026-08-26)**; these numbers move every tranche, so read `DISPATCH_COUNTY_FIPS` and `METRO_COUNTY_FIPS` in `scripts/build_metro_outline.py` as the authority, never this sentence). **THE APP LIVES UNDER `il/` AND SERVES AT `/il/`** (R2.3 — `docs/DEV_PROCESS_ASSESSMENT.md`). The repo is consolidating into one repo, one site: each state instance is a folder that serves at its own path, so the root can become the fleet landing page. `smoke_test.mjs` is a single end-to-end script, not a framework — there are no "individual tests" to select. It asserts the app boots, registers all layers, classifies a known downtown point against ground truth (school board 12, IL Supreme Court 1, Board of Review 3), and degrades to an isolated error card when a source fails. `node_modules`/`package.json` are intentionally gitignored — this repo never commits build artifacts.

**Sandboxed environments (Claude Code web) — Leaflet/MapLibre CDN egress:** every instance's `index.html` loads Leaflet and MapLibre GL (the vector-basemap renderer; the bridge plugin is committed same-origin at `<instance>/vendor/`) from `cdnjs.cloudflare.com`. In the Claude Code web/sandbox the headless browser cannot reach that CDN — Chromium doesn't use the agent HTTPS proxy, so the request resets (`ERR_CONNECTION_RESET` → `L is not defined` → the app never boots; a MapLibre-only failure is gentler — the app boots on its raster-fallback basemap). This is environmental, **not** a code regression; don't chase it in app code. It's handled automatically: a `SessionStart` hook (`.claude/settings.json`) runs `scripts/vendor_leaflet.sh`, which `curl`s both libraries (curl *does* go through the proxy) into **each instance's own** vendor dir — `scripts/vendor/leaflet/` for `il`, `ca/scripts/vendor/leaflet/`, `ny/scripts/vendor/leaflet/`, `wi/scripts/vendor/leaflet/`, `ia/scripts/vendor/leaflet/`, `mi/scripts/vendor/leaflet/` — because that is where each instance's `smoke_test.mjs` looks (it resolves `vendor/leaflet` next to itself). All six are gitignored; the smoke test then serves them same-origin via `page.route`, so the app boots. Production and GitHub Actions CI are untouched — they reach the CDN directly and the vendor dirs are absent, so the fallback is skipped. To vendor one instance manually, `bash scripts/vendor_leaflet.sh ca`; with no argument it does all six.

**That script is ONE script, and it fails loudly on a misconfiguration.** Three byte-identical copies used to live in `scripts/`, `ca/scripts/` and `ny/scripts/` — genuinely non-redundant while the instances were separate repos, because each self-located into its own tree, and pure duplication the moment they became folders under one root where only the root copy's hook ever fires. It also used to print a soft note and `exit 0` when it found no Leaflet URL, which is right for an unreachable CDN and wrong for a bad path: R2.3 moved the app to `il/` and left the script reading the repo-root `index.html`, now the redirect stub, so it skipped silently and the smoke test died 45 seconds later at `page.waitForFunction: Timeout` — the exact symptom the paragraph above tells you not to chase into app code. A missing app file or one with no Leaflet URL now exits 1 and names the instance; only a failed fetch stays best-effort.

`validate_index.py` is the merge gate: it confirms `index.html` passes `node --check`, still registers every layer (a drop in the `registerLayer(` count fails), embeds no dataset inline, that every `data/app/` file is present with the expected feature/roster counts, and that **`sources.html` still carries a matrix row for every registered layer and the app still links to it** — a layer whose provenance row is missing reads to a reader as a layer with no source, and a sources page nothing points at is a page nobody reads.

`validate_sources.py` is the **freshness** gate (complements the merge gate above). It catches the failure mode the roster scrapers can't: a publisher silently superseding a dataset the app hardcodes. Chicago Data Portal (Socrata) datasets are re-published under a **new id** each year — the CPS attendance-boundary layers ship a fresh `…SY####` dataset every school year — so the old id keeps returning stale data with no error. The script carries a manifest of every Socrata dataset id and shapefile provenance URL the app depends on and checks: (1) the manifest still matches index.html (drift guard), (2) each Socrata id still resolves and keeps its expected name, searching the portal catalog for a **newer-year edition** of the year-versioned ones, (3) the three shapefile sources (ilsenateredistricting.com / illinoiscourts.gov / cookcountyboardofreview.com) are reachable and their built `data/app/` files present, (4) the live ArcGIS/TIGERweb endpoints resolve. It **never edits the app** — swapping a dataset id is schema-sensitive — it exits non-zero only on hard FAILs and reports a newer edition as a WARN. `.github/workflows/validate-sources.yml` runs it monthly and opens/updates a single tracking issue on any WARN/FAIL (the job stays green; the issue is the signal), matching the roster pattern of "source changes get a human look before they ship." When a dataset id is swapped in index.html, update the manifest in `validate_sources.py` to match. **A source whose block is permanent and measured carries `"blocked": "<reason>"`** — seven do (Joliet, both McHenry sources, both Kendall sources, Lake board roles, the Chicago BOE early-voting page). For those the check INVERTS: unreachable is reported OK ("unreachable AS EXPECTED", still visible in the report), and becoming REACHABLE again is the WARN, because that is the state a human can act on — it means automation may be able to resume. Before that flag existed the monthly issue reopened with the same seven no-op WARNs every month. **HTTP 202 counts as unreachable**, not reachable: "Accepted" is never a document, and it is what the captcha fronts in front of several county sites return (dekalbcounty.org moved behind one around 2026-07-31 — its board scraper failed outright while this validator went on calling the source reachable, because 202 < 400).

`validate_card_links.py` is the **link** gate, and it watches the surface neither of the other two does: the URL a reader clicks. `validate_sources.py` covers dataset endpoints; nothing covered the `primaryLink` on a card or a roster's `sourceUrl` until Macon's card shipped `maconcountyil.gov` — a hostname with **no DNS record at all** — for three days (the county is at `maconcounty.illinois.gov`). It EXTRACTS its surface rather than carrying a manifest: `url:`/`href=` literals in **every authored HTML page** plus every http string in every instance's `data/app/*.json`, ~2,760 URLs across ~1,115 hosts, so a new county is covered the day it ships with nothing to update. **A new INSTANCE was not**, and that is the correction of 2026-08-28: "every authored HTML page" was a hand-kept list of fourteen, and Iowa shipped as the fifth instance with `ia/index.html`, `ia/faq.html` and `ia/sources.html` outside it — plus Iowa's whole `data/app`, since `APP_DATA_DIRS` named four instances out of five in the very commit whose comment says a new county is covered with nothing to update. **303 URLs, 52 of them authored, where a dead link would have stayed green forever.** Both lists are now DISCOVERED — every `*.html` at the root and in each instance folder, and one `data/app` per instance — where an instance is a top-level directory with its own `index.html` and `data/app/` (deliberately NOT `generate_metro_files.INSTANCES`: that import EXITS 1 without jsonschema, which the monthly workflow does not install, and it is not an ImportError so the usual guard does not catch it). Discovery also swept in the surfaces nobody had listed at all — the history pages, the per-concept SEO pages, and the root redirect shells, whose canonical is the only machine-readable record of where each pre-R5 path now forwards a reader. sources.html joined that list the day it shipped, and had to: it took ~40 authored URLs off index.html — the footer credit row plus one boundary link per layer — which scanning index.html alone would have silently dropped off this gate. Three things make its output readable instead of a monthly wall of other people's outages. (1) **Authored vs published.** A URL this repo chose (index.html, a builder's own `SOURCE_URL`) FAILs when dead — it is ours to fix. A URL carried through a roster (the `url`/`profileUrl` fields: a village's website exactly as its county clerk published it, one of which is literally `yahoo.com`) is capped at WARN, and a mere 403 on one is OK — CDN-fronted village sites refuse datacenter clients as a matter of course and there is nothing to do about it. (2) **`EXPECTED_UNREACHABLE`**, the same inversion as `validate_sources.py`'s `blocked` flag and for the same measured reason: six hosts are recorded as refusing this client (Cloudflare challenges, Akamai denials), refusal reads OK, and REACHABLE-again is the WARN. An entry cannot calcify — it also warns if the app stops citing the host, and the inversion caught its own author within an hour: a host recorded off a 429 answered 200 on the next run, which is why 429 is now treated as rate-limiting (back off, retry, and say the probe may have caused it) rather than as a block. (3) **Runtime-built URLs are not probed.** `url: "…/schoolprofiles/" + schoolId` is a prefix, not an address; cps.edu 404s it bare while every built per-school URL resolves, so concatenated literals are named in the report instead of reported dead. Two lessons are baked in from getting them wrong first: DNS is resolved **once per host with retries** (a flaky parallel lookup reported two live sites as having no DNS record), and a 403 from an egress proxy is not a 403 from a site — in the Claude Code sandbox github.com 403s with the proxy's own JSON body, so never record a host from a local run without checking who answered.

`check_roster_retention.py` is the **retention** gate, and it exists because every other roster guard measures the wrong thing. Each builder floors a COUNT — "Boone seats 12", "Brown seats 7" — and on 2026-08-08 every one of those passed while Brown County's seven published e-mail addresses were one commit from deletion: browncoil.org had switched on Cloudflare's e-mail obfuscation, so `mailto:` became `data-cfemail`, and the parser returned seven members carrying nothing. **Seven rows in, seven rows out, guard satisfied, contact gone.** Thirty of the 43 builders additionally floor a field or two (`MIN_EMAILS`, `MIN_PHONES`), which is better, but each floor is hand-set per county, 13 builders have none, and no floor anywhere covers a field nobody thought to name — a new field ships unguarded by construction. So this gate lives outside the builders: it compares every `data/app` roster against the same file at the change's base and asks whether each field still appears on about as many records as before. The shipped file is the baseline, so a field is protected the moment it first ships, with nothing to configure. It fails on a field that **vanishes** (was on ≥2 records, now none), on one that loses at least half its records AND at least 3 of them, and on a record count halving. It ignores new files, new fields and small drops — a member leaving moves these by ones and twos. **The subtlety that cost the first draft its first test: coverage is measured PER SOURCE, not per file.** Pooled across `il-county-commissioners.json`, Brown's seven vanishing e-mails read as 40 → 33, an 18% dip that passed every threshold; ten counties share that file and each can break alone, so each top-level key is measured on its own (files pooling more than 200 sources, like `municipal-officials.json`, stay file-level, where per-group thresholds would fire on every village that reshuffles a page). A legitimate mass change — a consolidated election emptying a column — is recorded in `ACCEPTED_DROPS` with a reason and a date rather than by loosening a threshold for everyone, and **every entry there is re-audited against the shipped tree on every run**: the docstring used to claim an entry "prints a line every run so an entry cannot rot quietly" and that was false the day after the drop merged, since an accepted drop is consulted only where THIS diff observes the field going away — so once it is on the base branch nothing observes it and the exception goes silent forever, a permanent hole in the gate with nothing saying so. Now each entry prints every run and FAILS when it is orphaned (its file or its source has left the tree) or stale (the field it excused is back on records), which is the property `validate_card_links.py`'s `EXPECTED_UNREACHABLE` and `validate_contrast.py`'s `ACCEPTED_SHORTFALLS` already had. Wired into `smoke-test.yml`, which is where roster refreshes land as bot PRs.

`check_cache_version.py` is the **cache** gate, and it guards the one thing a cache-first policy costs. Each instance's `sw.js` splits `data/app/*.json` in two: rosters are network-first, so a changed officeholder reaches a returning visitor at once, and boundary geometry is CACHE-FIRST, which is instant and works offline and reaches that visitor ONLY when `CACHE_NAME` changes. `sw.js` has said "bump CACHE_NAME whenever SHELL_URLS, GEOMETRY_URLS, or ROSTER_URLS change" since it was written, and that sentence was the entire mechanism — a comment addressed to whoever remembers to read it. On 2026-09-02 Wisconsin added seven counties across five PRs; every one rewrote `metro-outline.json`, the cache-first ring that draws the scope wash, and none bumped the cache, which had last moved three weeks earlier. **Returning visitors got the new supervisors on their cards and the old wash on their map, greying out the very counties that had just been added** — the app contradicting itself, with every gate green, because `validate_index.py` checks that each data file sits in exactly ONE of the two lists and that is a different question. The gate diffs the change against its base (the `check_roster_retention.py` shape, wired into `smoke-test.yml` beside it), takes the cache-first list from the BASE's `sw.js` because that is what a returning visitor already holds, and fails when any of those files changed while that instance's `CACHE_NAME` did not — naming the files and the fix. It deliberately does NOT ask for a bump on network-first files, which need none and whose weekly roster PRs would turn the bump into noise nobody reads, and it skips an instance with no `sw.js` at the base rather than failing a new one. It does not require an INCREMENT either: any different name evicts the old cache, which is the property that matters.

`validate_contrast.py` is the **legibility** gate, and it measures the one thing `build_brand_tokens.py` cannot: that gate proves every consumer carries the token file's values, and nothing proved the values were readable. `districtry/tokens/districtry.tokens.css` had 54 `aria-` attributes, 17 `:focus-visible` rules and a reduced-motion query behind it in the app, and not one number — measured on 2026-09-02, light `--faint` (`#9aa3b2`, the footer meta at 11px, placeholders, the metro name in the title) reads **2.5:1 on white**, below even the 3:1 WCAG asks of large text; the dark tier paints `color:#fff` on `--accent` `#a78bfa` at **2.7:1** across every primary button and on `--accent-deep` `#c4b0ff` at **1.9:1** on their hover and every pressed state; and the app's skip link was white on dark `--ink` `#ece9f4` at **1.2:1** — invisible to exactly the keyboard users it exists for, the one masthead element the skin never restyled, fixed the same day by porting the `--paper`-on-`--ink` pair the root pages already used. The gate tests an explicit `PAIRS` table — (foreground, background, role, the selector that paints it), mapped from every CSS surface rather than a cartesian product, because no regex can follow `color:` through the cascade to the ground four ancestors up — in both tiers, with dark composed over light exactly as the browser does it (the dark block redefines 25 tokens and inherits the rest), translucent values composited before measuring, and each role held to its own floor (4.5 text, 3.0 large text and UI parts, decorative dividers measured and never gated). The table was built from a rule-by-rule map of the five CSS surfaces: every paint that puts one brand token on another is a row (the OK line prints the row, tier-pair and gated counts, and those are the only totals the gate claims — an earlier docstring quoted map totals that did not sum), and what the map found that the token file does not own is named rather than measured: the engine's `--card-*` palette, the pre-rebrand navy, Leaflet's own chrome, the gap-kind indicators, the runtime `--layer-accent` and the skin's own `--dst-*` tints. **A ground is named per row**: dark `--brand-tint` is translucent, and the same `--muted` text on it reads 4.94:1 over `--paper` and 4.33:1 over `--surface` — one side of the floor each — so a row spells the opaque token under a translucent one (`brand-tint@surface` is the coverage map's legend hover), and the first draft, which composited every tint over `--paper`, passed that pair at 4.94 while the browser paints it at 4.33. This gate measures the brand; the card palette is the next gate's subject. **A shortfall is recorded, never silenced**: `ACCEPTED_SHORTFALLS` carries the measured ratio, a reason and a date, the same shape as `ACCEPTED_DROPS` and `EXPECTED_UNREACHABLE`, and the gate fails on anything new, on a recorded value that moves in either direction (a fix must retire the entry; a regression cannot hide behind it), and on an entry naming a pair nothing tests. Entries recorded at the gate's introduction are marked `decided=False` and print on every run until someone changes the token or writes down why not. `--report` prints every pair's ratio.

`validate_instance_registration.py` is the **fleet-registration** gate, and it exists because adding a state is not one edit. The instance is a folder, and nine other places have to learn its tag; five of them DISCOVER the fleet from the tree (`check_roster_retention.py`, `validate_card_links.py`, `build_dark_map_palette.py`, `validate_workflow_deps.py`, `fleet_status.py`) and need nothing, while four hand-kept tables (`build_history_page`, `build_landing_page`, `build_manifests`, `compose_app`), `metros.json` and THREE literal five-line lists inside `smoke-test.yml` are claims nobody measured. Twice the miss shipped: `validate_card_links.py` named four instances out of five in the very commit whose comment said a new county is covered with nothing to update (303 URLs, 52 authored, unwatched), and the retention gate pointed at `il/data/app` alone while a bot PR stripped `party`, `capitolOffice` and `districtOffice` from all 213 New York legislators and reported "222 roster files, no field lost its records". Both were found by hand, weeks apart. **The TREE is canonical, never a table** — a top-level directory with an `index.html` and a `data/app/` IS an instance, the same rule `validate_card_links.py` discovers by — because taking `generate_metro_files.INSTANCES` as truth would let the gate agree with itself about a sixth instance nobody registered. It names the file and the symbol to edit, and refuses to pass having found fewer than two instances.

**The coverage ring's own gate was in no workflow, and it validates a hand-kept list.** `build_metro_outline.py --check` compares the SHIPPED outline against each instance's `INSIDE`/`OUTSIDE` anchors; it never rebuilds from `METRO_COUNTY_FIPS` (that needs TIGERweb), so a county added to that tuple without an anchor was green by construction — the ring simply never got asked about it. That is how Wisconsin greyed out seven counties for two days with every gate passing. `check_anchor_registry()` now runs on both the check and build paths in all three statewide instances and holds the anchor list to the county list offline: one INSIDE anchor per served county, no county doubled, none both inside and outside. **The key shapes differ by instance and both are correct** — Illinois keys anchors `Place (County)` because its ring is a subset of its state, Wisconsin and Iowa by bare county name because their ring IS the state — so a check demanding either shape would fail two correct instances. The three `--check` runs are now in CI. A gate that can only be vacuous is the same failure one level up: `check_county_coverage_list` walks `registerCountyLayer` entries, which Wisconsin and Iowa have none of, so it printed "0 dispatched counties all inside the coverage ring" as though that were a result, under an unedited copy of Illinois's docstring naming Illinois counties. Wisconsin had already closed it with `check_coverage_ring_tracks_roster`; Iowa now has `check_coverage_ring_tracks_counties`, held to `ia-county-officers.json` and deliberately NOT to `ia-supervisor-members.json` — the wash claims where the STATEWIDE layers answer, all 99 counties, while the supervisor roster covers 17, a known roster gap rather than a coverage lie, so that comparand would fail a correct instance.

`validate_skills.py` is the **skills** gate, and it exists because `.claude/skills/` is a new class of hand-kept prose. A skill is loaded at the moment an agent starts a kind of task and carries only what `CLAUDE.md` and the docs of record do not — the ORDER of a procedure, the test that settles each decision, and the current names of the tables and files the steps hang on. Those names are copies of facts that live elsewhere, which is the drift class every other gate here guards: a skill that says run `scripts/build_foo.py --check` after the script is renamed, or open §2.5.1 for a checklist that moved to §3.5.1 in the guide's 2026-08-27 rewrite (which is where this file's own reference to the first-island checklist still pointed until the gate found it), sends an agent somewhere confident and wrong. So every backticked repo path must exist, every `§N.N` must be a heading in `docs/EXPANSION_GUIDE.md`, every `--flag` after a script must be one the script mentions, every ALL_CAPS identifier must appear in a file the same skill names, and the description must fit the ~1,000-character trigger surface. A path a skill names in order to say it is NOT there is read as the warning it is. It caught a stale pre-R2.3 `data/source/raw/` in the first skill written against it. The skills themselves — `steward`, `county-n-plus-1`, `new-state-instance`, `new-layer`, `municipal-officials` and the rest — point at the guide by section and at the code by path, never copy a table or a list that changes per county, and say in their preambles what they deliberately do not restate.

`validate_doc_counts.py` is the **stated-count** gate, and its subject is the fleet's most-repeated number: "N layers". It appears 32 times across 77 documents and **nothing compared one of them against a worksheet** — the adjacent gates miss it by construction, since `build_landing_page.py` GENERATES the root page's six `aria-label="…, N layers"` strings from `len(worksheet["layers"])` and `fleet_status.py` diffs layer IDS against the guidebook matrix weekly and WARN-only, which says nothing about a number typed into a sentence somewhere else. Four were wrong on introduction (2026-09-04), and **two of them were in `docs/press-list.json`** — the outbound press list, so Iowa's understated figure was the number a journalist would have been handed; a third was `docs/WI_PHASE2_PLAN.md`, whose present-tense claim about Wisconsin its own worksheet contradicted the day the line was written. The counts come from each instance's own worksheet, DISCOVERED from the tree the way `validate_instance_registration.py` discovers instances. **Its two hard cases are both attribution, and both were learned from false positives it produced on its own first run.** A count takes the nearest instance name on EITHER side, because `README.md`'s "**39 layers** ship in Illinois today" puts the name after and reading only backwards charged Illinois's 39 to a Michigan in the previous sentence — while nearest-wins is what keeps "NYC, SF, and Wisconsin (31 layers…)" off the first two names. And a totals line (`Chicago 39 · NYC 27 · … · Michigan 15 layers`, six counts sharing one "layers" token) is recognised only when it pairs three or more distinct instances with numbers, because **Wisconsin has a county named IOWA**: the guidebook's per-county supervisor list pairs that county with its seat count in a run of comma-separated county/number pairs, which is indistinguishable from a claim about the Iowa INSTANCE unless you count how many instances the line pairs. (The literal string is quoted in the gate's own docstring, which is safe to hold it because the gate deliberately does not scan scripts.) An instance name that is also a county name elsewhere in the fleet is permanent, so the discriminator has to be structural. `HISTORICAL_COUNTS` carries a past-tense count that has since been overtaken, in the `ACCEPTED_DROPS` shape (reason, date, re-audited every run, orphans FAIL) — and is EMPTY on introduction, which is a measurement rather than an omission.

## Architecture: stable core + pluggable layer modules

All inside `index.html`, wrapped in one IIFE. The full contract and per-thread build log live in `docs/BUILD_PLAYBOOK_1.md`; `docs/OPTIMIZATION_PLAYBOOK.md` holds measured optimization tasks. `docs/DATA_LAYER_GUIDEBOOK.md` is the fleet-wide layer inventory (concept × metro matrix, recorded drops, parity debts, backlog) — update it in the same change as any layer add/rename/remove; the weekly fleet-status run WARNs on drift. `docs/EXPANSION_GUIDE.md` is the **State Expansion Guide — the primary guide for all future expansion**, rewritten around the STATE instance on 2026-08-27 after Wisconsin's fourth phase (the previous edition was a metro/fork guide, and both halves of that framing are retired). Part 1 the governance taxonomy and the expansion invariant (a new unit adds dispatch entries and roster rows, never new layers), Part 2 standing up a new state instance `<tag>/`, Part 3 deepening a state county by county and city by city (§3.4 municipal governments, §3.5 the county-N+1 checklist, §3.5.1 the rules earned county by county), Part 4 the new-concept procedure, **Part 5 what Illinois's 91 counties and Wisconsin's four phases taught** — organized by the question each rule answers — and Part 6 the shared machinery. Consult it before any expansion or new-concept proposal. **This guide holds the rules; `DATA_LAYER_GUIDEBOOK.md` holds the record** — where they disagree the guidebook is what was measured. It supersedes the retired `METRO_EXPANSION` / `STATEWIDE_EXPANSION` / `COUNTY_LAYER_CONSOLIDATION` / `MUNICIPAL_COUNCILS` / `ILLINOIS_LAYER_STANDARDIZATION` docs (pointer stubs remain at the old paths; originals verbatim in `docs/archive/`).

**Core** provides: the Leaflet map, click-to-select + debounced Chicago-bounded Nominatim geocoder, a global `state` object `{selectedPoint, sequence, layersOn, ...}`, the layer registry + result-card framework, selected-boundary highlight, and URL-hash permalinks (`#point=lat,lng&layers=ward,school-board`). A small namespace is exposed as `window.ChiExplorer` for debugging.

**Shared utilities** (reuse these; don't reinvent):
- `sanitize(str)` / render via `textContent` — all external strings must go through one of these. Injecting scraped or API text as HTML is treated as a real security bug here.
- `pointInGeometry(pt, geometry)` — the point-in-polygon test every polygon layer's `query` uses.
- `fetchJSONWithRetry(url, opts, retries)` — the standard data-fetch path (retry + failure isolation).
- `haversineMiles(...)` — for the nearest-N layers, which use straight-line proximity instead of point-in-polygon (police/fire stations via the `registerNearestPointLayer` factory; `school-site` as a bespoke block).

**A layer module** is registered via `registerLayer({ id, group, label, overlay: {load, style}, query(point, seq), render(result) })`. `group` is one of `political | safety | schools | geography`. Overlays lazy-load their boundaries on first toggle and are cached; `query` runs locally against the cached geometry. Families of similar layers are built by factory helpers (`registerPolygonLayer`, `registerSchoolZone`, `registerCpsNetwork`, `registerIlgaChamber`, `registerNearestPointLayer`) — follow the existing factory when adding a sibling. The factories derive each layer's hover-popup identity (`hoverName`) from the same properties its card reads, so the two surfaces can't disagree; a bespoke `registerLayer` block declares `hoverName(feature)` explicitly. Optional contract field `pointOfInterest(result) => {label, address} | null` drops a geocoded map pin (used by the school-zone layers). Optional contract field `coverage(point) => boolean | Promise<boolean>` declares where a layer's data applies (location relevance): outside its coverage the layer *hides* — toggle block, card, map overlay, hover-snapshot row, relationship outlines, and query all suppressed — without touching `state.layersOn`, so `layers=` permalinks survive and the layer reappears when a selected point re-enters coverage; a throwing coverage test fails open (the layer runs as if undeclared). Chicago's city-scoped layers declare `chicagoCoverage` (ERSB tiling), the Cook-scoped layers `cookCountyCoverage` (CCBR tiling), and the Will/DuPage/Lake/Kane/McHenry/Kendall county layers `willCountyCoverage`/`dupageCountyCoverage`/`lakeCountyCoverage`/`kaneCountyCoverage`/`mchenryCountyCoverage`/`kendallCountyCoverage` (pre-built county outlines); layers that declare nothing behave exactly as before the field existed. Cross-county concept layers (`county-board`, `judicial-subcircuit`, `fire-district`, `park-district`, `library-district`, `county-precinct`) register through the fork-level `registerCountyLayer` dispatcher — one toggle holding a per-county entry table, coverage = the OR of its counties' tests; polygon-style entries reuse `polygonCountyEntry`, and adding a county to a shipped concept is a dispatch entry, not a new layer (`docs/EXPANSION_GUIDE.md` Part 2). An entry's coverage can be narrower than its county: `county-precinct`'s Cook entry uses `suburbanCookCoverage` (in Cook AND NOT in Chicago) because city precincts belong to the separate `ward-precinct` layer. Two engine loaders exist purely for metro forks and are unused by Chicago's own layers: `loadArcGISPaged` (transfer-cap paging) and `makeSocrataPointLoader` (point datasets whose coordinates live only in properties) — see `docs/EXPANSION_GUIDE.md` Part 4.

**Two invariants that pervade the code:**

1. **Stale-async guard via `sequence`.** Every point selection bumps `state.sequence`. Async work captures `seq` and bails (`if (seq !== state.sequence) return;`) when a newer point has been selected. Preserve this in any code that awaits between selection and render.

2. **Per-layer failure isolation.** Each result card is independent: a layer whose data source is down shows an error + Retry *inside its own card* and never affects the others. Never let one layer's failure throw out of its `query`/`render` into shared code.

**Result-card content order (fleet convention):** a card leads with the layer name (the card header), then the district identifier, then — wherever a verifiable source exists — the representative(s)/officeholder(s), the office location, contact info (phone/email), and a link to more detail, in that order. Deviations are allowed where the concept demands them (nearest-N lists, layers with no elected officer), but when identity, location, or contact data exists in a layer's source, surface it on the card rather than leaving it in the dataset. New layers and card edits follow this order; known gaps are recorded in `docs/DATA_LAYER_GUIDEBOOK.md`'s **gaps block** and ship as `<instance>/data/app/coverage-gaps.json` — NOT in its backlog, which the guidebook itself warns is mostly a completion log where grepping for open work "returns mostly noise". The largest card-order gap WAS `county-board-office-addresses`, and it is now the instance's clearest case of a source being judged by the wrong column: **17 of Illinois's 63 districted board cards name no office**, down from 50 on 2026-09-06. Thirteen counties publish a board address of their own; 33 more take one from ISBE's County Officers Book — the SAME document whose chair-name column is read nowhere here because it disagrees with the counties' own rosters at a rate that must always be quoted WITH ITS DATE — 16 of the 56 counties then comparable (29%) on 2026-08-20, 23 of 75 (30.7%) on a fresh rebuild 2026-09-06, moving because the comparable set grows as counties ship rosters rather than because the document decays — and whose address column is a different column with a different failure mode (a chair turns over every cycle, a courthouse does not move). `scripts/build_county_board_offices.py` gates it two ways on every build: the address ships only where a second courthouse office on the same county page prints the same street and city, and it must keep agreeing with all seven counties that publish their own. A county's own publication always wins and `validate_index.py` fails if the two ever overlap. That gate also derives the comparison from the dispatch table on every PR — because the county list used to be hand-kept and went stale at the speed the frontier moves — and fails whether the record understates the absence or overstates it.

**Honesty rules (non-negotiable, enforced in review):** officeholder data is never guessed. Where no verifiable roster source exists, cards link to the official body instead of inventing a name. External strings are always sanitized or set via `textContent`.

## Data pipeline

Most layers fetch live public APIs at runtime (Chicago Data Portal / Socrata, CPD ArcGIS, Cook County GIS, Census TIGERweb, Nominatim). Layers with **no public API** ship their data as same-origin files under `data/app/`, fetched on first toggle:

- **Boundary geometry** (`school-board-districts.json`, `il-supreme-court-districts.json`, `ccbr-districts.json`, the pre-built `{congress,il-senate,il-house}-districts.json` from TIGERweb via `scripts/build_legislative_boundaries.py`, and `will-county-outline.json` for the coverage test) — mapshaper-simplified from the full-precision GeoJSON in `il/data/` (originals in `il/data/source/raw/`). Regenerate with `scripts/build_embedded_boundaries.py` (rare operator step). Service worker serves these **cache-first** (boundaries change ~once a decade).
- **Officeholder rosters + curated lists** (`il-{senate,house}-members.json`, `congress-roster.json`, `cpd-district-info.json`, `ccpsa-district-councils.json`, `will-county-board-members.json`, `kane-county-board-members.json`, `lake-county-board-roles.json` — regenerated **weekly by CI** from scraper output; `kendall-county-board-members.json` + `mchenry-county-board-members.json` hand-verified (those counties block all automated fetch incl. the Internet Archive's crawler — their weekly workflows attempt an engine ladder and track the block on standing issues); `school-board-members.json` hand-curated; `early-voting-sites.json` hand-transcribed per election). Service worker serves these **network-first** so a returning visitor never gets a stale officeholder. Officeholder sourcing for any NEW county/metro layer is determined and built in the same change that ships the boundary (`docs/EXPANSION_GUIDE.md` Part 2 rule 4).

**Scraper → builder pattern** (each roster has a pair): a `*_scraper.py` produces intermediate JSON, a `build_*.py` writes the `data/app/*.json` file with count guards (it refuses to write if too few records resolve). `scripts/requirements.txt` pins deps; the CPD scraper additionally needs Playwright for a Cloudflare managed-challenge fetch. Builders emit plain JSON via `json.dump` into `data/app/`, and the app renders every external string through `sanitize()`/`textContent` — together that closes the injection surface for scraped text. (The historical `js_string()`-style `</script>` + U+2028/U+2029 escaping guard existed only when data was spliced directly into the HTML; it closed a real injection bug then, and becomes mandatory again only if scraped text is ever spliced into HTML/JS — don't.)

## CI workflows (`.github/workflows/`)

- `smoke-test.yml` — runs the behaviour gate on every PR and push to `main`, plus the static drift gates and **`check_roster_retention.py`**, which compares every roster field against the change's base and fails when one stops being published. It checks out with `fetch-depth: 0` for that reason. This is the gate that would have caught Brown's seven e-mails going silently empty; roster refreshes land here as bot PRs, which is exactly where it needs to fire.
- `update-{ilga,congress,cpd,ccpsa,will-county-board,ccbr,county-clerk}-roster.yml` — weekly (staggered) roster refreshes. Each re-scrapes, rebuilds `data/app/`, runs `validate_index.py`, and — if anything changed — **opens a PR rather than committing to `main`.** Officeholder data always gets a human review before it ships. Match this pattern for any new roster: never auto-commit roster changes to `main`.
- **`BOT_PR_TOKEN` (repo secret) — why every roster PR runs CI.** A PR opened with the default `GITHUB_TOKEN` fires **no** workflows: GitHub suppresses recursive triggers, so the smoke test never ran on a bot PR and the PR page showed zero checks. All 13 PR-opening workflows now check out and open their PR as `BOT_PR_TOKEN` instead. It needs Contents **read/write** (push the `bot/*` branch) + Pull requests **read/write** (open it) on this repo — the same shape as `ENGINE_DISPATCH_TOKEN`. Every reference is `${{ secrets.BOT_PR_TOKEN || github.token }}`, so an absent or expired secret degrades to the old behaviour (a PR with no checks) rather than breaking the refresh — which also means **a silently expired PAT looks exactly like the bug it fixed**: if bot PRs stop showing checks, check the token before anything else. Data is still gated either way, because each workflow runs `validate_index.py` on the rebuilt files before opening the PR; the PAT is what makes that visible on the PR itself.
- `validate-sources.yml` — monthly source-freshness check. Runs `scripts/validate_sources.py` **and `scripts/validate_card_links.py`**, folding both reports into one issue; on any WARN/FAIL (e.g. a Socrata dataset superseded by a newer-year edition, or a shapefile source gone unreachable) it **opens or updates a single tracking issue** rather than editing anything — the job stays green, the issue is the signal. Same "surface for a human, don't auto-apply" convention as the roster PRs. The issue title is matched to update in place, so it stays `Layer source drift detected — review needed` even though it now carries link findings too — renaming it would orphan the open issue.
- `fleet-status.yml` — weekly (Mon 15:00 UTC) fleet aggregator. **CORRECTED 2026-09-02**: this bullet used to describe `scripts/fleet_status.py` as comparing CHI against separate fork repos (engine-pin drift, a cross-fork `docs/ENGINE_SYNC.md` diff) — that was accurate before R5 and stale after it, since every metro is now a folder in this one repo. The script was already updated in step with the consolidation (it reads instance files off this checkout, not over the API, and the two fork-comparison checks were removed rather than left to report a trivial "in sync" against themselves); the doc just hadn't caught up. What it actually checks now, per instance in `metros.json`: a `validate_index.py` `CAPABILITIES` reverse-parity diff against CHI's, scraper health (flagging a workflow file that isn't in the shared root `.github/workflows/` as **INERT** — it looks like a live refresh and never runs), a workflow-basename-collision check (two instances can't both own one root-level filename), the instance's layer roster diffed against `docs/DATA_LAYER_GUIDEBOOK.md`'s coverage map, and its shipped `data/app/coverage-gaps.json` diffed against the guidebook's gaps block (also gated directly in CI since 2026-09-02, so this is now a second weekly-cadence check rather than the only one). CHI-only: its own `docs/ENGINE_SYNC.md` inventory checked against the real ENGINE fences (`index.html`/`sw.js`) — the file that says "the SAME copy ships in every fork" had drifted 164 lines with an inventory naming 50 blocks against 53 real fences, because `check_engine_parity.py` compares fenced CODE and nothing compared the document — plus a list of open `bot/*` PRs awaiting human review. Reports on a single standing issue (#138); the job never fails.
- Engine release machinery — **RETIRED in R2.1** (`release-engine.yml`, `create-engine-tag.yml`, `engine-parity.yml`, `update-state-template.yml` deleted along with `apply_engine.py`, `build_engine_artifact.py`, `build_state_template.py`, `bootstrap_state.py`, `check_template_placeholders.py`, `templates/state/` and `engine.lock.json`). One repo, one copy of the engine, no fan-out.
- `deploy-pages.yml` — publishes `main` to GitHub Pages (chidistricts.com).

## Conventions

- Code style is ES5-flavored (`var`, `function` expressions) throughout `index.html` — match it when editing existing modules.
- The "verified" date shown in the UI lives in `metro-worksheet.json` as `verified_date`; bump it there and regenerate when reverifying data sources. It used to be hand-written near the boot block in `index.html`, which was fine while one surface printed it — `sources.html` prints it too, and two hand-kept copies of one date is how they drift, so both are now GENERATED regions off that one key.
- This is a public-facing civic tool that explicitly disclaims legal precision — accuracy and the honesty rules matter more than feature velocity.

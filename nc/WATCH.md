# WATCH.md — North Carolina's watch calendar and deferred measurements

Two things live here: *when to look* for boundary and roster changes in this instance's
sources, and the measurements this instance has taken but not yet acted on. The repo's
`docs/REDISTRICTING_RUNBOOK.md` is *what to do* when a boundary changes. Update the
"Last done" column each time you complete a row — a checkpoint with a stale date is a
checkpoint that didn't happen.

The two roster jobs are in the standing table above. The files below have no job, because
a weekly job on a boundary would almost always find nothing to change. Each row says what moves
the file and when to look. A `--check` proves a file matches what it was built from; it never
proves the source is still current.

|---|---|---|---|
| **On 3 January 2027**, then annually when TIGERweb rolls its congressional vintage, and on any redraw | `congress-districts.json` | **THE MAP MUST BE THE ONE THE SERVING MEMBERS WERE ELECTED FROM, AND THE NEWEST VINTAGE IS NOT.** Go-live shipped TIGERweb layer 0, the 120th Congress's map that North Carolina redrew in 2025 for the 2026 election, beside a roster of members elected in 2024 from the 119th's. The two differ in districts 1 and 3: 15.3% of the state's area changes district, and Goldsboro and Kinston, which Rep. Don Davis (District 1) represents, read as District 3. Found by the next-five-states planning thread and measured 2026-10-09; the file now ships layer 4, the 119th's map. **On 3 January 2027 switch back**: point the builder at the layer named "120th Congressional Districts" with its CD120 field, rebuild, and bump `cache_name`. | **Annually**, when TIGERweb publishes a new county vintage | `state-counties.json`, `metro-outline.json` | Both come from the same 100-county TIGERweb fabric, and the outline is that fabric dissolved, so they share one clock. `nc/scripts/build_metro_outline.py --check` tests the shipped ring against its 100 inside anchors, so it would catch a lost county and would not notice a redrawn line. | **Annually**, on the TIGERweb vintage roll | `tribal-areas.json` (2 areas, the Eastern Band of Cherokee Indians') | *Not a redistricting at all* — tribal land changes when the United States takes land into trust, which is published on no calendar. `scripts/build_tribal_areas.py --check` re-derives the shipped file from `data/tribal-government-join.json` and the BIA directory OFFLINE, so it proves the join and NEVER that the Census has not added or removed an area — only a rebuild does that (`python3 scripts/build_tribal_areas.py --state "North Carolina" --tag nc`). | **Annually**, and in the same change as any new North Carolina layer or roster | `coverage-gaps.json` | This file is emitted from the guidebook's gaps block, and `build_coverage_gaps.py --check` compares the two on every pull request, so the file cannot drift from the record. The yearly clock is for the RECORD: `nc-commissioner-districts` rests on a catalogue search measured 2026-09-29, and a county that starts publishing its districts moves that finding with nothing to detect it | **_(never)_**, written 2026-09-29; 2026-10-16 (`nc-municipal-officeholders` rewritten with the city council layer) |
| **Quarterly** | `nc-precincts.json` | Each county board of elections changes its own precincts, and the State Board of Elections posts the statewide shapefile as dated zips in one folder; NC OneMap serves the queryable copy this builder reads, which carries no date of its own and was matched to the 2026-08-24 zip by its counts. Run `nc/scripts/build_nc_precincts.py --watch`, which asks two questions. Has NC OneMap's copy changed? `--watch` reads every record's key, name, county and area, with no geometry, and compares them with the fingerprint recorded when the shipped file was built; on a change it names the counties whose precinct counts moved. Then rebuild with the builder, which re-runs the exact count, the every-county check, the 6,000-point agreement gate and the per-county cover check and refuses to write if any fails. A new count is changed by hand, in the builder's `expect` and in `data_files.geometry`, and never widened into a range; check the precinct anchor in the worksheet, bump `cache_name` because the file is cache-first, and say which counties moved. And has the Board posted a zip newer than `SBE_PRECINCTS_20260824.zip`? A newer zip with the copy unchanged means NC OneMap has not loaded it yet: wait and re-check, because the card names the Board file the copy matches (August 24, 2026). When the copy does change, match it to the new zip before rebuilding, then change `BUILT_FROM` in the builder; the builder refuses to build, and its `--check` fails, until the card names that file's date | 2026-10-15 (built: 2,625 precincts in 100 counties; `--watch` unchanged, newest Board file 2026-08-24, the same day) |
| **Weekly**, by `.github/workflows/watch-city-council-pages.yml`, and by hand again in the weeks after each place's own election | `nc-city-councils.json` | Each of the 42 cities and towns lists its own mayor and council and changes the page when a seat changes hands, at no fixed time. Most North Carolina places elect in November of odd years and some in even years (Raleigh, Asheville and Winston-Salem among them), so the weeks after each November are when most pages move. The weekly job runs `nc/scripts/build_nc_city_councils.py --watch`, which re-reads every page the seats file cites, asking robots.txt first, reports any name no longer on its page and any page it cannot read, and opens or updates one tracking issue for all five states, "City council pages need a re-read", which the next run that reads every page and finds every name closes; the same command can be run by hand. On a report, read the place's page, change `nc/data/source/nc-city-council-seats.json` by hand (a new member, a changed seat, or the page's own spelling as `as`), and rebuild with the builder, which re-reads every page and refuses to write unless every name is on the page it cites. A place that adds or drops a seat changes `SEATS` in the builder; one that starts or stops electing by district changes the seats' `by`, which moves the district map too (the next row) and `WARD_MAPS` in `scripts/build_eam_status.py`. Durham's, Greensboro's, Cary's, Greenville's, Rocky Mount's, Garner's and Wilson's pages are read with a browser's client because each refuses this project's own (measured 2026-10-16), so a NOT READ line for one of them means re-measuring with `scripts/probe_user_agents.py` before changing anything. Raleigh's and Matthews's names come from the State Board's results because both websites answer with a managed challenge; each quarter, read each place's robots.txt and home page once with this project's own client, and if either serves its council page, cite that page instead | 2026-10-16 (built: 304 seats in 42 places, every name found on its page) |
| **Quarterly**, and after each decennial census, when the cities redraw their districts | `nc-city-wards.json` | A city redraws its districts by ordinance, usually after a census and sometimes after an annexation, and five of the seventeen maps are published by the city's county rather than the city, so a map can change when either edits it. Run `nc/scripts/build_nc_city_wards.py --watch`, which re-reads each map and compares it with the fingerprint recorded when the shipped file was built; on a change, rebuild with the builder, bump `cache_name` because the file is cache-first, and run `nc/scripts/build_nc_city_councils.py --check`, which holds every drawn district to a seat its voters elect. Durham, Concord, Hickory and Morrisville tie seats to districts or wards and elect every seat by the whole place, so their districts are not drawn; a session law or charter change that has a district's own voters elect its member would add that city here | 2026-10-16 (built: 100 districts in 17 cities) |

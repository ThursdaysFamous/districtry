# WATCH.md — Georgia's watch calendar and deferred measurements

Two things live here: *when to look* for boundary and roster changes in this instance's
sources, and the measurements this instance has taken but not yet acted on. The repo's
`docs/REDISTRICTING_RUNBOOK.md` is *what to do* when a boundary changes. Update the
"Last done" column each time you complete a row — a checkpoint with a stale date is a
checkpoint that didn't happen.

---

## Re-check plan for each data file the app reads

The two roster jobs are in the standing table above. The files below have no job, because a
weekly job on a boundary would almost always find nothing to change. Each row says what moves the
file and when to look. A builder's `--check` proves a file matches what it was built from; it
never proves the source is still current.

| Cadence | File | The clock, and why it is that one | Last done |
|---|---|---|---|
| **Annually**, and on any court order or new act | `congress-districts.json`, `ga-senate-districts.json`, `ga-house-districts.json` | All three are the General Assembly's own shapefiles of its December 2023 plans, pinned by SHA-256. The office versions its file URLs, so a replaced file is a new URL and a changed one stops the build. `python3 ga/scripts/build_legislative_boundaries.py --check-listing` reads the office's page and confirms each pinned file is still listed under the plan it was chosen as | 2026-10-29 (built, listing checked) |
| **Annually**, when TIGERweb publishes a new county vintage | `state-counties.json`, `metro-outline.json` | Both come from the same 159-county TIGERweb fabric, and the outline is that fabric dissolved, so they share one clock. `ga/scripts/build_metro_outline.py --check` tests the shipped ring against its 159 inside anchors and its 20 outside anchors in all five neighbouring states, so it would catch a lost county and would not notice a redrawn line | **_(never)_**, built 2026-10-29 |
| **After each election with county contests**, and whenever the map office lists a new or changed county map | `ga/data/source/county-map-check.json` (read by the build, served to nobody) | The record of which county commission and school board maps the precincts that voted agree with. It is only as current as its newest ballot: a county that redraws its districts or its precincts after it moves the answer, and nothing else notices. `python3 ga/scripts/check_ga_county_maps.py --check` (in CI) proves each verdict follows from its contests, not that the contests are the newest | 2026-10-30 (written; contests to 16 June 2026) |
| **After each county map check** | `ga-commission-districts.json`, `ga-school-board-districts.json`, `ga-board-district-counties.json` | The drawn county commission and school board districts and what the check said of each. They change only when the record does: `ga/scripts/build_ga_board_districts.py` draws exactly the maps the record passes, from the office's files the check tested (pinned by SHA-256 in the record), and `python3 ga/scripts/build_ga_board_districts.py --check` (in CI) holds the three files to the record offline. The two district files are cache-first, so a rebuild that changes them bumps `cache_name`; the counties file is network-first | 2026-10-30 (built) |
| **Annually**, and in the same change as any new Georgia layer or roster | `coverage-gaps.json` | This file is emitted from the guidebook's gaps block, and `build_coverage_gaps.py --check` compares the two on every pull request, so the file cannot drift from the record. The yearly clock is for the RECORD: each gap rests on a measurement with a date, and a publisher that starts publishing moves that finding with nothing to detect it | 2026-10-29 (written with the instance) |

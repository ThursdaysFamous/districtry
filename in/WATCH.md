# WATCH.md — redistricting watch calendar

The one place the dates live: *when to look* for boundary and roster changes in this
instance's sources. The repo's `docs/REDISTRICTING_RUNBOOK.md` is *what to do* when a
boundary changes. Update the "Last done" column each time you complete a row — a
checkpoint with a stale date is a checkpoint that didn't happen.

This instance arrived on 2026-09-29 with eleven layers, every one of them from a national
publisher, and exactly one roster. So this file is short on purpose: most of what a mature
instance watches here is a county or city publisher, and Indiana has none of those yet.

## Re-check plan for each data file the app reads

Every file the app fetches is re-checked on a stated clock. The roster
(`congress-roster.json`) has a weekly job, in the standing table above. The six files below
have no job, because a weekly job on a boundary would almost always find nothing to change.
Each row says what moves the file and when to look. A `--check` proves a file matches what it
was built from. It never proves the source is still current, which is why the files with a
gate of their own are still listed here.

| Cadence | File | The clock, and why it is that one | Last done |
|---|---|---|---|
| **Annually**, when TIGERweb rolls its congressional vintage, and again on each decennial redraw (next: 2031–2032) or any court-ordered mid-decade one | `congress-districts.json` | The vintage roll is the yearly clock. It renames the district field (`CD119` became `CD120` on 2026-09-03), and the old name is rejected rather than kept, so the per-decade table above names the field to change. The redraw is the decennial clock, enacted by the General Assembly as ordinary statute (IC 3-3-2). Rebuild with `in/scripts/build_legislative_boundaries.py`. It rebuilds all three chamber files together, so this row and the next one are re-checked in the same run | **_(never)_**, built 2026-09-29 |
| **After each decennial census** (next: 2031–2032), and on any mid-decade or court-ordered redraw | `in-senate-districts.json`, `in-house-districts.json` | The General Assembly draws both chambers itself (IC 2-1-1), so the signal is a redistricting bill rather than a commission calendar. The chambers do not nest (see the per-decade table), so a rebuild re-measures the partition gate and never adds a nesting one | **_(never)_**, built 2026-09-29 |
| **Annually**, when TIGERweb publishes a new county vintage | `state-counties.json`, `metro-outline.json` | Both come from the same 92-county TIGERweb fabric (`State_County/MapServer/1`), and the outline is that fabric dissolved, so they share one clock. County lines almost never move; what can move is TIGER's digitisation of them. `in/scripts/build_metro_outline.py --check` does not re-fetch. It tests the shipped ring against the 92 inside anchors, so it would catch a lost county and would not notice a redrawn line. Re-run `in/scripts/build_state_counties.py` and `in/scripts/build_metro_outline.py` against the new vintage and compare | **_(never)_**, built 2026-09-29 |
| **Annually**, and in the same change as any new Indiana layer or roster | `coverage-gaps.json` | This file has no upstream of its own. It is emitted from the guidebook's gaps block, and `build_coverage_gaps.py --check` compares the two on every pull request, so the file cannot drift from the record. The yearly clock is for the RECORD. `in-county-government` rests on a measured count: council districts for 56 of 92 counties on the Indiana Geographic Information Office's statewide layer (2026-09-29). A county that starts publishing moves that count and nothing detects it, which is how a gap record goes stale. The other five records describe work this instance has not done yet, so each one changes when that work ships | **_(never)_**, written 2026-09-29 |
